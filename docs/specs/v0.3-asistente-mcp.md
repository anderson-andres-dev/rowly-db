# Asistente integrado con memoria de negocio — diseño

## Estado

**Diseño.** Nada implementado todavía. Este documento es la fuente de verdad:
cada subtarea registra su estado, lo decidido y lo que falta.

Última actualización: 2026-09-27. Revisado con Codex (gpt-5.6-sol); sus
observaciones aceptadas ya están incorporadas.

## Objetivo

Un asistente de IA **dentro de Rowly DB**: el panel del asistente abre el
agente que el usuario ya usa (Claude Code, Codex, Gemini CLI, Kimi Code),
tal cual, en una terminal integrada. El agente llega sabiendo quién es, qué
es Rowly DB, qué puede hacer y qué hay en la base, sobre la conexión que el
usuario tiene abierta, sin configurar nada más.

- "¿Qué día se hacen las facturas?" → lo deduce de los datos una vez y lo
  recuerda.
- "¿Cuántas facturas válidas tiene este cliente?" → aplica la regla "solo
  son válidas desde 2023", que no está en la base sino en la memoria.
- "Dame las facturas válidas de marzo" → deja el SQL en una consola y
  muestra el resultado en el data grid; en la terminal solo dice dónde.
- "Cambia el tema", "oculta el sidebar" → lo hace, con guardarraíles.
- El mismo agente, abierto desde la terminal del sistema, también puede
  conectarse a Rowly DB.

Nombres: **Rowly DB** es el nombre comercial y el único que ve el usuario
o el agente (textos de la interfaz, instrucciones, skill, nombre del
servidor MCP: `rowly-db`). **Khipu** es el nombre interno del motor: solo
en crates (`khipu-*`) y código.

## Principios

- **El que piensa es Rowly DB, no la IA.** Rowly DB arma el contexto justo para
  cada pregunta (reglas, términos, tablas y columnas relevantes) y lo
  entrega compacto. Con buen contexto, hasta un modelo básico sirve, y se
  gastan pocos tokens.
- **El agente es el del usuario.** Rowly DB ejecuta el CLI oficial, con su
  login y su suscripción; no construye un chat propio ni toca credenciales
  de IA. Es la forma más simple y la más limpia con los términos de uso de
  cada proveedor.
- **Mostrar, no dibujar.** Los datos se muestran en la interfaz de Rowly DB
  (consola y data grid), no como texto en la terminal (6).
- **Memoria agnóstica de la IA.** La memoria es de Rowly DB, no de un modelo:
  cambiar de agente no pierde nada.
- **Aprender una vez.** Lo analizado queda guardado con la huella de lo que
  se analizó; no se repite mientras no cambie.
- **Solo lectura por defecto.** Escribir en la base se habilita únicamente
  por decisión expresa del usuario, nunca del agente.
- **Memoria local, contexto al proveedor.** La memoria se guarda en los
  datos de la app de cada usuario y nunca se sube a ningún repositorio.
  Lo que el agente usa (esquema, reglas, resultados) sí viaja al proveedor
  del agente elegido; la interfaz lo dice así, sin prometer "nada sale del
  equipo".
- **La seguridad está en el código.** Las guardas de la base y de la app
  viven en el servidor MCP de Rowly DB, no en las instrucciones al modelo:
  valen aunque el agente las ignore.
- **Zen.** El panel del asistente se abre bajo demanda y devuelve el foco
  a donde estaba.

## 1. Arquitectura

```
               ┌────────────────── Rowly DB (app/src-tauri) ────────────────────┐
               │                                                                │
 Panel del     │   terminal integrada (xterm.js ↔ PTY)                          │
 asistente ◄───┼──► claude · codex · gemini · kimi   (CLI oficial, tal cual)    │
               │          │  MCP streamable HTTP, 127.0.0.1, token de sesión    │
               │          v                                                     │
               │   crates/mcp  herramientas + puente a la interfaz              │
               │          │                                                     │
               │          ├── crates/memory   memoria .md + índice SQLite        │
               │          ├── crates/engine   guard del asistente, parser        │
               │          └── drivers         conexión de la sesión              │
               │                    ▲                                           │
               └────────────────────┼───────────────────────────────────────────┘
                                    │ mismo servidor, token propio
                        el mismo CLI abierto desde la terminal del sistema
```

Piezas, cada una sin saber de Tauri (la app les inyecta la conexión, el
catálogo y los comandos, igual que `engine` con `SchemaCatalog`):

1. **Terminal integrada** (`app/src-tauri` + frontend): un PTY en Rust y
   xterm.js en el panel, con el tema de la app. Lanza el CLI del agente
   dentro de la carpeta de sesión (1, "Carpeta de sesión").
2. **`crates/agents` — perfiles de lanzamiento.** Por agente: cómo se
   lanza, cómo se le pasa el MCP, dónde lee instrucciones y skills, cómo se
   desactivan sus herramientas propias. Genera la carpeta de sesión.
3. **`crates/mcp` — herramientas.** Un solo servidor para el agente del
   panel y para el que se abra desde fuera. Hace de puente con la interfaz
   (consolas, data grid, tema) (6).
4. **`crates/memory` — el cerebro.** Memoria permanente y de trabajo en
   `.md` por base de datos, con un índice derivado (2).

### Sesiones atadas a una conexión

- Cada sesión de agente queda atada a **una ventana** y a **una instancia
  de conexión** (`connection_instance_id`: cambia en cada conexión, aunque
  sea al mismo perfil). Hoy `AppState` tiene una conexión activa por
  ventana; la sesión usa esa y ninguna otra. El token de la sesión es lo
  que la ata: cada token vale para una sola sesión.
- Desconectar o cambiar de conexión: se cancelan las consultas en curso,
  se revocan todos los permisos y el token de la sesión deja de valer. El
  agente puede seguir abierto (su historial es suyo), pero las
  herramientas le responden «sesión terminada: abrir una nueva». La base
  nueva abre una sesión nueva. Así nunca se mezclan esquema, reglas o
  filas de dos bases.

### Agentes soportados

| Agente | CLI | MCP | Instrucciones | Skill | Estado |
|---|---|---|---|---|---|
| Claude | `claude` | `--mcp-config` + `--strict-mcp-config` | `CLAUDE.md` | `.claude/skills/` | Primera versión |
| Codex | `codex` | `-c mcp_servers.rowly-db…` | `AGENTS.md` | `.agents/skills/` | Primera versión |
| Gemini CLI | `gemini` | `settings.json` de la sesión | `GEMINI.md` / `AGENTS.md` | por confirmar | Después |
| Kimi Code | `kimi` | por confirmar | `AGENTS.md` | por confirmar | Después |

- Opciones y rutas **a confirmar en 20a** contra la versión instalada de
  cada CLI. Cada perfil declara una versión mínima.
- Rowly DB detecta cuáles están instalados y ofrece solo esos. Si el
  agente pide iniciar sesión, lo hace su propio CLI, dentro de la
  terminal; Rowly DB nunca ve el login.
- **Claude con suscripción**: se ejecuta Claude Code, la app oficial, con
  el login del usuario. Riesgo conocido: Anthropic anunció y luego pausó
  (junio de 2026) descontar parte del uso de terceros de unos créditos
  aparte. Rowly DB no depende de un solo proveedor: el usuario cambia de
  agente cuando quiera.
- La cabecera del panel muestra siempre qué agente y qué proveedor están
  activos.

### Carpeta de sesión

Rowly DB crea una carpeta privada por sesión y lanza el CLI dentro:

```
assistant/sessions/<sesión>/
├── CLAUDE.md / AGENTS.md          instrucciones de sesión (2b), mismo contenido
├── .claude/skills/rowly-db/       la skill (2b), según el agente
├── .agents/skills/rowly-db/
└── mcp.json                       servidor rowly-db + token de la sesión
```

- La skill y las instrucciones se copian **en la carpeta de sesión**, no en
  la configuración global del usuario (`~/.claude`, `~/.codex`): no se le
  ensucia su agente y siempre va la versión que corresponde a la app.
- La carpeta no contiene datos de la base: solo instrucciones y
  configuración. Se borra al cerrar la sesión.

### El agente encerrado por defecto

- Se lanza con sus herramientas propias **desactivadas**: terminal, leer y
  editar archivos, web (`--disallowedTools` en Claude, `--sandbox
  read-only` y aprobaciones en Codex). Solo le quedan las herramientas de
  Rowly DB.
- **Prueba automática por agente y versión**: lanzado con su perfil, el
  agente no puede leer un archivo fuera de su carpeta, ejecutar un comando
  ni abrir una URL. Si una versión nueva no la pasa, su perfil se marca
  como no probado y la interfaz lo avisa.
- **Límite honesto**: es la sesión del usuario. Si él reactiva herramientas
  desde dentro de su agente, lo que el agente haga con ellas queda fuera
  de Rowly DB. Lo que Rowly DB garantiza es la base y la app, porque eso
  pasa por el MCP.
- Todo lo que viene de la base (filas, nombres, comentarios del DDL) se
  entrega marcado como **contenido, nunca instrucciones**. Es una ayuda
  para el modelo, no una barrera.

## 2. La memoria (`crates/memory`)

### Dos tipos de memoria

| | Permanente | De trabajo |
|---|---|---|
| Qué es | Lo que el negocio es: reglas, aclaraciones, términos, estructura de tablas | Lo que se está haciendo: "mañana seguimos con esto", "esto quedó pendiente" |
| Ejemplo | "Una factura es válida desde 2023"; "estado 3 = anulada"; "cliente = `abonado`" | "Conciliación de marzo: faltan las notas de crédito del 12 al 15" |
| Quién escribe | El agente propone, el usuario confirma | El agente la crea y la actualiza sola |
| Vida | No caduca. Solo se descarta a mano | Abierta → cerrada. Al cerrarla: **guardar un resumen en el historial** o **borrarla** |
| Contexto | Siempre disponible, las reglas primero | Los pendientes abiertos, una línea cada uno, al abrir sesión |

Cerrar una tarea nunca toca la memoria permanente. Si de una tarea salió
algo del negocio ("descubrimos que las notas de crédito se anulan con
estado 9"), al cerrarla Rowly DB ofrece convertirlo en una aclaración
permanente, con la confirmación de siempre.

### Estructura de tablas: primero la memoria, después la base

Cada tabla analizada queda en su propio `.md`. El orden para conocer una
tabla es siempre:

1. **Su `.md` en la memoria.** Si la huella coincide con el catálogo
   actual, se usa tal cual: cero consultas a la base y cero análisis
   repetido.
2. **El catálogo** (ya cargado en RAM al conectar): si la tabla no tiene
   `.md` o su huella cambió, Rowly DB genera la parte de estructura sin gastar
   tokens de IA y la guarda.
3. **Explorar los datos** (`profile`): solo si hace falta entender los
   valores. Lo observado se guarda en el mismo `.md`.

El `.md` tiene dos partes: la **estructura**, que Rowly DB regenera cuando la
huella cambia, y lo **aprendido** (para qué sirve, aclaraciones, lo
observado), que se conserva siempre. Si la estructura cambió, lo aprendido
queda marcado "por revisar", sin borrarse.

```markdown
---
id: t_7f3a2c
format: 1
kind: table
table: ventas.factura
fingerprint: 9c1e…
analyzed: 2026-09-27
updated: 2026-09-27T10:15:00Z
---
## Estructura
id pk int · abonado_id fk→ventas.abonado.id · fecha_emision date
estado smallint · total decimal(12,2) · creado_en timestamp
índices: (abonado_id, fecha_emision)

## Aprendido
Facturas emitidas a clientes. Una fila por factura, no por línea.
- estado: 1 emitida · 2 pagada · 3 anulada  (aclarado por el usuario)
- fecha_emision: días 1–5 de cada mes  (observado 2026-09-20)
- ver [[factura-valida]]
```

Los `[[enlaces]]` son las aristas del grafo: regla ↔ tabla, término ↔
tabla, tabla ↔ tabla (FK).

### Huella de una tabla

- Se calcula sobre una **representación normalizada y versionada del
  catálogo** (columnas, tipos, nulabilidad, claves, índices), no sobre el
  texto del DDL: un DDL reformateado no cambia la huella.
- Se valida al conectar y al refrescar el schema. Un cambio hecho desde
  fuera se detecta en el siguiente refresco; mientras tanto vale la última
  validada.
- El análisis es perezoso y solo sobre los schemas visibles
  (`set_visible_schemas`): una tabla de un schema oculto no se analiza.

### Consistencia de los `.md`

Los `.md` son la fuente de verdad, así que se escriben con cuidado:

- Front matter obligatorio: `id` estable, `format` (versión del formato),
  `kind`, `status`, `origin`, `updated`.
- El nombre del archivo es seguro y estable (derivado del `id` y un slug
  saneado), independiente del título: renombrar una regla no mueve el
  archivo.
- Escritura atómica: archivo temporal + renombrar. Un cierre inesperado
  nunca deja un `.md` a medias.
- Un bloqueo por base: dos ventanas no escriben la misma memoria a la vez.
- `index.sqlite` se reindexa en una transacción, después de escribir.
- Un `.md` inválido (editado a mano y roto) queda en cuarentena, con un
  aviso; no rompe el resto de la memoria.
- Cambios de formato: migraciones explícitas por versión de `format`.

### Dónde vive cada cosa

**Memoria del usuario: nunca en el repo.** Va en la carpeta de datos de la
app (la misma que usa `console_texts.rs`): Linux
`~/.local/share/com.khipudb.app/`, macOS
`~/Library/Application Support/com.khipudb.app/`, Windows
`%APPDATA%\com.khipudb.app\`.

```
com.khipudb.app/assistant/
├── memory/
│   └── 3f9a…c21/                    una carpeta por base de datos (HMAC)
│       ├── tablas/
│       │   ├── ventas.factura.md
│       │   └── ventas.abonado.md
│       ├── negocio/                 permanente
│       │   ├── reglas/
│       │   │   └── factura-valida.md
│       │   ├── terminos/
│       │   │   └── cliente.md
│       │   └── consultas/
│       │       └── facturas-validas-de-un-cliente.md
│       ├── trabajo/                 de trabajo
│       │   ├── abiertos/
│       │   │   └── 2026-09-27-conciliacion-marzo.md
│       │   └── historial/
│       │       └── 2026-09.md       resúmenes de lo cerrado, uno por mes
│       └── index.sqlite             derivado: búsqueda y aristas
├── behavior.md                      reglas de comportamiento propias del usuario
├── sessions/<sesión>/               carpeta de sesión (1); se borra al cerrarla
└── log/2026-09.jsonl                registro de lo que hicieron los agentes
```

- **La fuente de verdad son los `.md`**: legibles por cualquier IA o
  persona, agnósticos del modelo. `index.sqlite` es solo un índice
  (búsqueda, aristas) y se reconstruye entero desde los `.md` si se borra.
- La carpeta de cada base es un **HMAC** (hash con una clave secreta local,
  guardada en el llavero) de motor + host normalizado + puerto + base. Un
  hash simple se podría adivinar probando nombres; con la clave, no. La
  memoria es de la base, no de quién se conecta: dos usuarios de la misma
  base comparten reglas. "Olvidar esta base" es borrar su carpeta.
- Las **columnas sensibles** se marcan en el `.md` de la tabla.
- El **token** del servidor externo va al llavero del sistema, como las
  contraseñas (`credentials.rs`). Los permisos "hasta desconectar" viven
  solo en RAM.
- El historial de trabajo no se envía al agente salvo que lo pida
  (`history(query)`).
- El **registro** guarda qué se hizo, no los datos: herramienta, SQL con
  los literales reemplazados, filas y columnas devueltas, permisos. Nunca
  el contenido de un resultado.
- Registro y sesiones rotan por mes, con retención configurable, y hay un
  botón «Borrar conversaciones y registro de esta base».

**En el repo de Rowly DB**: el código de `crates/memory`, `crates/mcp`,
`crates/agents` y la UI; la configuración por defecto (`crates/agents/`:
perfiles de lanzamiento, instrucciones de sesión y la skill, 2b); fixtures
de prueba inventados, nunca datos reales.

### Salud de la memoria

La memoria es el cerebro del asistente: si se llena de ruido, cada
respuesta gasta más tokens y acierta menos. Guardar es una decisión, no un
reflejo. Hay dos barreras: las reglas que sigue el agente y los controles
que aplica Rowly DB aunque el agente no las siga.

**Reglas del agente** (en la plantilla de comportamiento, 2b):

- Antes de guardar, buscar si ya existe. Si existe, actualizarla; no
  crear un duplicado.
- Guardar solo lo que no se puede obtener de otra forma. La estructura
  sale del catálogo; los resultados de una consulta se vuelven a consultar.
- `summary` contiene una sola idea, en una línea. `detail` es opcional:
  evidencia breve, procedencia y el SQL que la verifica.
- No guardar filas ni datos personales: nombres, documentos, correos,
  teléfonos, montos de un cliente concreto. Se guarda la regla, no el caso.
- Guardar lo verificado. Una deducción no comprobada se marca como tal.
- Si algo nuevo contradice una nota, proponer reemplazarla; no guardar las
  dos.
- En la memoria de trabajo, cerrar lo terminado en cuanto termina.

**Controles de Rowly DB** (no dependen del agente):

- `remember` y `work` buscan notas parecidas antes de crear. Si hay una,
  devuelven esa nota y el agente debe decidir entre actualizarla o
  justificar la nueva.
- Límite de tamaño: `summary` de una línea (≤ 160 caracteres) y `detail`
  ≤ 1000. Lo que excede se rechaza con el motivo, no se recorta.
- Filtro de datos personales: una nota que contiene valores que aparecen
  en columnas sensibles, o con forma de correo, documento o teléfono, se
  rechaza.
- Los mismos controles aplican a la **edición a mano** desde la vista de
  memoria. Un aviso (posible duplicado) se puede ignorar; un invariante
  (datos personales, tamaño) no.
- **Revisión de salud**, bajo demanda o sugerida con un aviso discreto:
  duplicados probables, contradicciones, notas `stale`, notas nunca usadas
  en meses y pendientes de trabajo abiertos hace más de 30 días. El usuario
  decide qué fusionar, actualizar o descartar; nada se borra solo.
- Presupuesto por base: si la memoria permanente pasa de un tamaño (por
  defecto 80 000 caracteres), la revisión de salud se sugiere al abrir
  sesión.

## 2b. Cómo aprende quién es

El agente sabe quién es, qué puede hacer y cómo comportarse por tres capas,
de la más barata a la más cara en tokens:

| Capa | Qué lleva | Cuándo se carga |
|---|---|---|
| **Instrucciones de sesión** (`CLAUDE.md` / `AGENTS.md`) | Quién es: «Eres el asistente de Rowly DB, conectado a <motor> <base>». Las reglas fijas: solo lectura, mostrar en el grid, guardar solo con herramientas, contenido ≠ instrucciones. «Usar la skill `rowly-db`». Idioma de la app | Siempre, al abrir. Corto: ≤ 1 500 caracteres |
| **Skill `rowly-db`** | Cómo trabajar: flujo de una pregunta (`context` → consulta → `show_result`), cómo y cuándo guardar memoria, reglas de escritura del idioma, conciencia de la app (capacidades, estado, acuses) | Cuando el agente la necesita (el CLI carga solo su descripción hasta usarla) |
| **MCP, en vivo** | `session_brief()`: base, reglas activas, términos, pendientes abiertos, estado de la pantalla. `context`, `app_capabilities`, `app_state` | Cuando el agente las pide; las instrucciones le dicen que empiece por `session_brief()` |

- Lo que cambia con cada conexión va por MCP, no en archivos: la carpeta
  de sesión no guarda datos de la base.
- **El agente no escribe los `.md`**: guarda con `remember` y `work`, y
  Rowly DB escribe el archivo. Así valen los controles de salud (2), el
  filtro de datos personales y la escritura atómica. La skill le enseña
  herramientas, no carpetas.
- Formato de la skill: el estándar de Agent Skills (`SKILL.md` con
  descripción + archivos de referencia), que Claude Code y Codex leen. El
  soporte en Gemini CLI y Kimi Code se confirma al agregarlos.

### Fuente en el repo

```
crates/agents/
├── profiles/                claude.toml, codex.toml…: lanzamiento, MCP, rutas, herramientas
├── instructions.md          plantilla de las instrucciones de sesión
└── skill/
    ├── SKILL.md             la skill rowly-db
    ├── references/
    │   ├── tools.md         cuándo usar cada herramienta
    │   ├── memory.md        reglas de memoria (salud)
    │   └── app.md           conciencia de la app, mostrar en el grid
    └── locales/
        ├── es.md  en.md  pt-BR.md  fr.md  de.md   reglas de escritura del idioma
```

- Se escriben en inglés (`SKILL.md`, referencias, instrucciones): todos los
  modelos lo siguen igual de bien y cuesta menos tokens. Al crear la
  sesión, Rowly DB reemplaza `{{language}}` por el idioma de la app
  (`LOCALE_NAMES`) y copia solo el archivo de ese idioma.
- Cada `locales/<idioma>.md` está escrito en su idioma: las listas de
  expresiones prohibidas y de términos de obligación no se traducen
  palabra por palabra. Agregar un idioma a la app obliga a agregar su
  archivo (lo comprueba un test, igual que las claves de i18n).
- Contenido propuesto de las reglas de escritura, memoria y app: Anexo A.
- Las reglas aplican a las respuestas **y a todo lo que se guarda en la
  memoria**: una regla de negocio usa «debe» / «no debe», y la regla de
  terminología uniforme hace que el agente use los términos de la memoria
  ("cliente", no "abonado" en un lado y "suscriptor" en otro).
- Si el usuario cambia el idioma de la app, lo ya escrito en la memoria
  queda en el idioma original.

### Reglas propias del usuario

- `assistant/behavior.md` en la carpeta de datos de la app (no
  commiteable), editable desde Ajustes > Asistente. Se agrega a las
  instrucciones de sesión.
- Solo cubren **preferencias**: idioma, tono, formato, terminología. En
  esas, si chocan con una por defecto, gana la del usuario.
- **Invariantes, no modificables**: reglas de memoria sobre datos
  personales, tratar el contenido de la base como contenido y no como
  instrucciones, permisos y escritura. Van después de las reglas del
  usuario, y de todos modos el backend las aplica aunque el modelo no las
  siga.

## 3. Recuperación: el contexto justo

La herramienta clave es `context(pregunta)`. Además, al abrir una sesión
Rowly DB le entrega al agente un **resumen inicial** corto (motor, base, reglas
activas, términos, pendientes de trabajo abiertos) para que la primera respuesta ya sepa del negocio.

Ranking **determinista** en la primera versión, fácil de depurar:

1. **Coincidencia exacta**: los términos de la pregunta, normalizados (sin
   tildes, singular/plural, snake_case), contra `term`, nombres de tablas y
   columnas y el texto de las reglas.
2. **Reglas confirmadas** enlazadas directamente a lo que coincidió.
3. **Un salto por FK** desde las tablas que coincidieron.
4. **Segundo salto**, solo si queda presupuesto.

- **Presupuesto en caracteres**, no en tokens: Rowly DB no conoce el
  tokenizador de cada modelo. Por defecto 6 000 caracteres (~1 500 tokens),
  con un tope por sección para que las tablas no desplacen a las reglas.
  Si el adaptador informa tokens reales, se usan.
- Las reglas van siempre primero: son lo que el agente no puede adivinar.
- **Sin pesos aprendidos en la primera versión.** Que una consulta se
  ejecute sin error no prueba que la respuesta fuera correcta, y los pesos
  harían que lo ya usado se use cada vez más, desplazando reglas raras
  pero críticas. Se guardan contadores de uso solo como estadística local
  para revisar el ranking; el refuerzo se decide después, con datos reales.

Sin embeddings en la primera versión.

### Formato compacto

El agente recibe texto denso, no JSON verboso. Ejemplo para "¿cuántas
facturas válidas tiene el cliente 1234?":

```
REGLAS
! C r_12 factura válida: fecha_emision >= '2023-01-01' AND estado <> 'ANULADA'
TÉRMINOS
C t_03 cliente = abonado
TABLAS
abonado(id pk int, codigo varchar uq, nombre varchar, ruc varchar)
factura(id pk int, abonado_id fk→abonado.id, fecha_emision date, estado enum[EMITIDA,ANULADA,PAGADA], total decimal)
HECHOS
O f_40 factura.fecha_emision: días 1–5 de cada mes (2026-09-20)
```

- Solo las columnas relevantes más las claves; el resto se pide con
  `describe`.
- Marca de procedencia en cada nota: `C` confirmada, `O` observada
  (perfilado), `U` sin verificar (propuesta pendiente), `S` por revisar
  (stale). Y su `id`, para que el agente la cite o la actualice.
- Todo texto que viene de la base o de una nota se escapa: saltos de línea
  y caracteres de control se neutralizan y cada campo tiene un largo
  máximo. Un nombre de columna no puede fabricar una línea `REGLAS`.

## 5. Guardarraíles de datos

### Lectura

- **Estructura siempre disponible**, sin permiso: catálogo, reglas,
  términos, tablas y hechos ya guardados.
- **Permiso de acceso a datos** para todo lo que sale de los datos: filas,
  agregados (`COUNT`, `SUM`...), `profile`. Un agregado también filtra
  datos: `GROUP BY email` o `COUNT(*) WHERE documento LIKE '1%'` repetido
  reconstruyen valores. Rowly DB pregunta **en su propia interfaz** (nunca
  se deja al agente), con la consulta a la vista:
  - Permitir esta consulta
  - Permitir en esta sesión (hasta desconectar)
  - Denegar
- "Esta consulta" queda atada al hash del SQL exacto, la sesión y la
  instancia de conexión; "en esta sesión", a la sesión y la conexión.
  Ninguno sobrevive a una desconexión.
- **La primera vez por proveedor y conexión**, el aviso dice también a
  quién se envía: «El resultado se enviará a Claude (Anthropic)».
- **Columnas sensibles**: marcadas por el usuario. En la primera versión,
  `query` rechaza toda consulta que las nombre, las incluya con `*` o las
  use en una expresión. No se promete enmascarar: `concat(email, '')`
  esquivaría una máscara. El agente puede dejar esa consulta en una
  consola con `open_console` para que la ejecute el usuario.
- Timeout (por defecto 15 s, también del lado del servidor cuando el motor
  lo permite: `max_execution_time` en MySQL, `statement_timeout` en
  PostgreSQL) y límite de filas por consulta (por defecto 50), con aviso
  "resultado truncado" al agente.

### Escritura

- **Guard propio del asistente** (`validate_assistant_statement`, en
  `crates/engine`), que niega todo por defecto. El `execution_guard`
  actual no sirve tal cual: fuera de Producción deja pasar `INSERT` sin
  confirmación y trata `USE` como lectura. Sin modo escritura solo pasa una
  `SELECT` demostrablemente de lectura: nada de `USE`, `SET`, `CALL`,
  `SELECT … INTO`, lecturas con bloqueo (`FOR UPDATE`), DML dentro de un
  CTE ni sentencias que el parser no reconozca.
- **Y además**, en la **misma conexión** tomada del pool:
  `START TRANSACTION READ ONLY` (MySQL) / `BEGIN READ ONLY` (PostgreSQL),
  la consulta y `ROLLBACK`. Doble barrera: el modo de solo lectura del
  motor no es absoluto (MySQL deja modificar tablas temporales, y una
  función puede tener efectos), por eso el guard va primero.
- Funciones con efectos conocidos (leer archivos del servidor, `sleep`,
  administrativas) se bloquean por lista. Se recomienda en la interfaz una
  cuenta de base con los privilegios mínimos.
- **Modo escritura** (después de la primera versión): lo activa **solo el
  usuario**, con un control en el panel, para esa sesión. Ni el agente ni
  un agente de fuera pueden activarlo ni pedirlo por herramienta.
- Con el modo escritura activo, cada sentencia se muestra y se confirma. La
  confirmación es un **comprobante de un solo uso** emitido por el backend
  y atado al hash del SQL exacto, la instancia de conexión, la sesión y
  una expiración corta. El backend vuelve a analizar el SQL y consume el
  comprobante de forma atómica. La confirmación actual (que solo compara la
  categoría de la sentencia) no se reutiliza para esto.
- En conexiones de **Producción** el modo escritura no está disponible
  desde el asistente, comprobado en Rust, no solo en la interfaz; el
  agente puede dejar el SQL con `open_console`.
- La sesión vuelve a solo lectura al cerrar el panel, desconectar o
  cambiar de conexión.

### Siempre

- Solo sobre la instancia de conexión a la que está atada la sesión (1).
  El agente no puede conectar, cambiar de conexión ni leer perfiles o
  credenciales.
- Todo queda en el **registro del asistente**: quién (agente de dentro o de
  fuera), herramienta, argumentos, resumen de lo devuelto, permisos pedidos
  y concedidos.

## 6. Manejar la app

El agente puede usar toda la app, como lo haría el usuario con el teclado,
y debe saber qué hizo y dónde quedó. Ejemplo de respuesta:

> Dejé la consulta en una consola nueva, «facturas_validas», y abrí su
> resultado abajo, en la pestaña «Asistente · facturas válidas»: 1 284
> filas.

Para eso hay tres piezas: qué puede hacer (capacidades), qué hay en
pantalla (estado) y qué pasó con cada acción (acuse).

### Mostrar, no dibujar

La regla central del asistente. La terminal es para conversar; los datos se
ven en Rowly DB.

- **Respuesta con datos en forma de tabla** (más de una fila, o varias
  columnas): el agente deja el SQL en una consola suya (`open_console`) y
  abre el resultado en el data grid (`show_result`). En la terminal, una
  línea: qué hizo y dónde mirar. Nunca dibuja la tabla en la terminal.
- **Respuesta de un solo valor** («¿cuántas facturas válidas?»): lo dice en
  la terminal (1 284) y deja el SQL en una consola, para verificarlo.
  Abrir una pestaña del grid para un número sería ruido.
- **Pedidos sobre la app** («cambia el tema»): lo hace con `app_action` y
  confirma en una línea.
- La regla va en las instrucciones de sesión (siempre cargadas) y se
  detalla en la skill.

### Capacidades: un registro con tipos

Las capacidades salen de las mismas fuentes que describen la app, sin una
lista paralela escrita a mano:

- **Comandos** (`commands.ts`): los mismos que usan los atajos, la hoja de
  atajos y el futuro vim mode.
- **Ajustes**: tema, fuente, idioma, posición del asistente…

Hoy ninguna de las dos alcanza: `CommandDefinition` solo tiene `id`, zona,
grupo y teclas; los handlers no reciben argumentos y devuelven
`boolean | void`, y los ajustes no están en ningún registro. 20h las
extiende con:

- política para el agente, esquema de argumentos, precondición (cuándo
  aplica) y clase de efecto;
- un resultado estructurado (efecto y ubicación) en vez de `boolean`;
- un puente Rust ↔ frontend: el MCP vive en Rust y los handlers en el
  frontend. Rust envía la petición con un id, el frontend la ejecuta y
  responde el acuse con el mismo id. **La política se vuelve a comprobar
  en Rust**, no solo en el frontend.

Cada entrada gana una **política para el agente**:

| Política | Qué significa | Ejemplos |
|---|---|---|
| `free` | La ejecuta sin preguntar. Solo cambia lo que se ve y se deshace cerrando o volviendo atrás | Abrir consola, abrir pestaña de resultado, formatear una consola del agente, mostrar/ocultar sidebar, paginar |
| `undoable` | La ejecuta y muestra «El asistente cambió X · Deshacer» | Tema, tamaño de fuente, cambiar un atajo, posición del asistente |
| `confirm` | Pide confirmación en el panel antes de ejecutar | Cerrar una consola con cambios sin guardar, escribir en una consola del usuario |
| `never` | No existe para el agente | Credenciales, perfiles de conexión, conectar/desconectar, borrar o sobrescribir archivos, ajustes del propio asistente (permisos, modo escritura, token, políticas) |

- **La política por defecto es `never`.** Un comando o ajuste nuevo no
  queda al alcance del agente hasta que alguien lo decide.
- **Un test obliga a declarar la política** de cada comando y cada ajuste.
  Agregar una función sin decidir qué puede hacer el agente con ella rompe
  el build. Así el registro se actualiza con cada función nueva.
- El nombre y la descripción que ve el agente son **los mismos textos de
  i18n que ve el usuario** (`i18n/messages/shortcuts.ts`), en el idioma de
  la app. El agente llama a cada cosa como se llama en pantalla, y no hay
  una segunda descripción que mantener.
- Los argumentos de cada capacidad (qué tema, qué atajo) se declaran junto
  al comando o ajuste y se validan igual que desde Ajustes. Cambiar un
  atajo pasa por la misma validación de choques que Ajustes > Atajos.
- **Primera versión**: el registro con tipos completo, pero solo con estas
  capacidades habilitadas: `open_console`, `show_result`, mostrar/ocultar
  sidebar, cambiar tema. Las demás quedan en `never` y se habilitan una a
  una después, cada una con su test.

### Reglas propias de la IA sobre la app

- El SQL del agente va siempre a una **consola nueva** creada por él, o a
  una que él creó en la sesión. Escribir en una consola del usuario es
  `confirm`: nunca pisa texto del usuario sin permiso.
- Las consultas del agente abren su resultado en una **pestaña propia** del
  panel de resultados, marcada como del asistente. No reemplazan la
  pestaña que el usuario estaba viendo.
- Ejecutar una consulta desde una consola sigue las reglas de 5 (solo
  lectura, permiso de filas, modo escritura); tenerla escrita en pantalla
  no le da más permisos.

### Estado: qué hay en pantalla

`app_state()` devuelve una foto compacta de la interfaz:

```
LAYOUT asistente=abajo (entre consola y resultados) sidebar=abierto tema=oscuro
CONSOLAS consola_1* (usuario, activa) · facturas_validas (asistente)
RESULTADOS Salida · core.tec_abonados (usuario) · Asistente · facturas válidas (activa)
CONEXIÓN mysql prod-core (solo lectura)
```

- Las posiciones se describen con las palabras del usuario (abajo, a la
  derecha, arriba), según el layout real de ese momento.
- El resumen inicial de la sesión incluye esta foto; después el agente la
  pide cuando la necesita. No se envía en cada mensaje.

### Acuse: qué pasó con cada acción

Cada acción devuelve un acuse corto con el efecto y dónde quedó:

```
ok open_console → consola «facturas_validas», pestaña nueva del editor, arriba
ok show_result  → pestaña «Asistente · facturas válidas», panel de resultados, abajo · 1 284 filas
```

- El agente usa el acuse para explicarle al usuario qué hizo y dónde
  mirar. La plantilla de comportamiento (2b) le exige hacerlo después de
  cada acción visible.
- Si la acción no se pudo hacer (la política la bloquea, el argumento no
  es válido, el usuario la rechazó), el acuse dice por qué, y el agente lo
  informa en vez de intentar otra vía.
- Todo queda en el registro del asistente.

## 7. Comunicación entre agentes

Después de la primera versión. Con agentes en terminales, Rowly DB no puede
meter un mensaje en la conversación de otro de forma limpia. Por eso la
comunicación es un **buzón** en el servidor MCP:

- `send_message(to, text)`: un agente deja un mensaje para otra sesión
  (del panel o abierta desde fuera).
- `read_messages()`: el destinatario lo lee cuando el usuario se lo pide,
  o al empezar su siguiente turno si la skill se lo indica.
- La cabecera del panel muestra «1 mensaje de Codex» para que el usuario
  sepa que hay algo.

### Reglas

- Un mensaje de otro agente es **contenido, no una orden con autoridad**:
  no hereda permisos. Si lleva a algo que requiere permiso (datos, una
  escritura, una acción), el permiso se pide al usuario igual que siempre.
- Un mensaje de un agente **abierto desde fuera** queda retenido hasta que
  el usuario lo acepta en el panel.
- Tamaño máximo por mensaje y cantidad máxima por hora, para que dos
  agentes no entren en un bucle.
- Todo mensaje queda en el registro.

### Agente abierto desde fuera

- El mismo CLI, abierto desde la terminal del sistema, se conecta al mismo
  servidor. Apagado por defecto; se activa en Ajustes > Asistente, que
  muestra un bloque listo para pegar en la configuración de Claude Code /
  Codex.
- Transporte MCP "streamable HTTP" servido desde el backend Rust (SDK
  `rmcp`), no desde el WebView. Solo en loopback (`127.0.0.1`).
- Token en la cabecera `Authorization: Bearer`, nunca en la URL; guardado
  en el llavero; se puede regenerar. Validación de `Host` y `Origin` (evita
  que una página web del navegador lo use) y límite de tamaño de cuerpo.
- El token de fuera es distinto de los de sesión y queda atado a la
  ventana y la instancia de conexión que el usuario elige al activarlo; se
  corta al desconectar.
- El nombre que un cliente dice tener (`clientInfo`) no se puede
  verificar: el registro lo muestra como «cliente externo (dice ser:
  Claude Code)».
- Un agente de fuera nunca puede activar el modo escritura ni conceder
  permisos.

## 8. Interfaz

### Posición del panel

El asistente es un panel del área de trabajo, no una ventana del sistema.
Tiene dos posiciones:

```
 Entre consola y resultados              A la derecha
 ┌──────────────────────┐                ┌───────────────────┬──────────┐
 │ consola              │                │ consola           │          │
 │                      │                │                   │ asistente│
 ├──────────────────────┤                │                   │          │
 │ asistente            │                ├───────────────────┤          │
 ├──────────────────────┤                │ resultados        │          │
 │ resultados           │                │                   │          │
 └──────────────────────┘                └───────────────────┴──────────┘
```

- **Entre consola y resultados**: para media pantalla. El flujo se lee de
  arriba abajo: lo que se escribe, lo que se conversa, lo que se obtiene.
- **A la derecha**: para pantalla completa. Ocupa todo el alto del área de
  trabajo, junto a la consola y los resultados.

Ajuste en Ajustes > Asistente > Posición:

- **Automática** (por defecto): se decide por el **ancho del área de
  trabajo** (sin el sidebar), no de la pantalla. Pasa a la derecha cuando
  el área mide ≥ 1280 px y vuelve al medio cuando baja de 1180 px. Los dos
  umbrales distintos evitan que salte mientras se redimensiona cerca del
  límite. Los valores se ajustan al probarlo.
- **Entre consola y resultados** / **A la derecha**: fija, sin importar el
  ancho.
- Comando `move-assistant` (sin atajo por defecto): alterna la posición y
  deja la posición en manual.

Al cambiar de posición, la terminal no se reinicia: el agente sigue en el
mismo proceso, con su conversación, su scroll y el foco.

### Tamaños

- Cada posición recuerda su propio tamaño: alto en el medio, ancho a la
  derecha (por defecto 380 px). Se cambian arrastrando el borde, como el
  sidebar (`sidebarLayout.ts`).
- **En el medio, el panel se pliega** a mano (comando `collapse-assistant`)
  a solo su cabecera (~32 px): el agente sigue corriendo y la cabecera
  avisa si hay algo en la franja. Media pantalla no alcanza para tres
  paneles completos.
- Mínimos: la consola y los resultados conservan su alto mínimo. Si no
  caben, el asistente se pliega primero.
- Soltar el arrastre por debajo del mínimo cierra el panel, igual que el
  sidebar.

### Abrir, cerrar y foco

- `Alt+2` abre el asistente y le da el foco; si ya tiene el foco, lo
  devuelve a la zona de donde se llegó. Cerrar el panel es su propio
  comando (`close-assistant`).
- Nueva zona de foco `assistant`. Hoy `focusZones.ts` tiene cuatro zonas
  fijas en una cuadrícula 2×2 (`neighborZone`); con el asistente, los
  vecinos se **calculan desde el layout visible** (posición del panel,
  sidebar oculto).
- Pila de foco anterior (`previousFocus`): hoy `Esc` desde una zona que no
  es el editor vuelve siempre al editor; eso no aplica a la terminal.
- Cerrado no deja rastro en pantalla (principio zen).
- Tests de foco para las dos posiciones, panel cerrado y sidebar oculto.

### Teclado dentro de la terminal

La terminal y el agente usan muchas teclas (`Ctrl+W` borra una palabra,
`Esc` interrumpe al agente, `Ctrl+C`, `Ctrl+R`…). Los atajos se adaptan para
no chocar:

- Con el foco en la terminal, **todas las teclas van a la terminal**,
  salvo un conjunto corto de **teclas reservadas de la app**: `Alt+1`,
  `Alt+2` y las de la franja de avisos (abajo). Nada con `Ctrl+letra` ni
  `Esc` queda reservado.
- `Ctrl+W` (prefijo de foco) y `Esc` (cancelar consulta) no actúan dentro
  de la terminal. Para salir de ella: `Alt+2`.
- Cada comando declara si actúa dentro de la terminal. Ajustes > Atajos
  comprueba los choques también contra la lista de teclas de terminal:
  no deja asignar una tecla de terminal a un comando que actúa dentro de
  ella.
- Todo esto con `Alt+`: el agente de cada CLI casi no usa `Alt`, a
  confirmar en 20a con Claude Code y Codex.

### Contenido del panel

```
┌ Claude · Anthropic   mysql prod-core   solo lectura ─────────────── ✕ ┐
│ ⚠ Permitir leer datos: SELECT … FROM factura …   [Permitir] [Denegar] │  ← franja, solo si hay algo
├────────────────────────────────────────────────────────────────────────┤
│ terminal: el agente, tal cual                                          │
└────────────────────────────────────────────────────────────────────────┘
```

- **Cabecera mínima**: agente y proveedor, conexión, indicador de modo
  (solo lectura / escritura), mensajes del buzón.
- **Franja de avisos**, encima de la terminal, solo cuando hay algo: pedido
  de acceso a datos (con la consulta a la vista), propuesta de memoria
  (Confirmar / Editar / Descartar), confirmación de una acción `confirm`.
  La herramienta del agente espera la respuesta (con timeout, que cuenta
  como rechazo).
- La franja **no roba el foco** de la terminal (teclado primero): se
  responde con `Alt+Y` / `Alt+N` desde la terminal, o yendo a ella con el
  teclado. Teclas a confirmar en 20a.
- **La terminal**: el CLI del agente, con el tema y la fuente de la app.
- La conversación queda en el historial del propio CLI. Rowly DB conserva
  el registro de lo que el agente hizo, porque todo pasa por el MCP.

### Otras vistas, bajo demanda

- **Memoria de la base**: reglas, términos, tablas, hechos, consultas
  guardadas y pendientes de trabajo; crear, editar y descartar a mano, sin
  IA. Se abre desde el panel o el explorador y ocupa el lugar del panel
  mientras está abierta.
- **Registro del asistente**: lista cronológica de todo lo que hicieron
  los agentes, de dentro y de fuera.
- **Ajustes > Asistente**: posición, agentes detectados, agente por
  defecto, presupuesto de contexto, timeout y límite de filas, reglas de
  comportamiento propias, servidor externo (activar, puerto, token).
- Todo operable por teclado; textos por i18n en los 5 idiomas.

### `base.md`

````markdown
# Writing rules

You are the assistant of Rowly DB, a database client. Apply these rules to every answer and to everything written into the memory.

1. Write in {{language}}, neutral and professional. Follow the language rules below.
2. Use short, direct sentences.
3. Prefer impersonal or infinitive instructions.
4. Do not write unnecessary introductions, decorative conclusions or promotional language.
5. State each rule once. Do not repeat it in another section.
6. Do not use the ambiguous expressions listed for the language.
7. Express every obligation with the explicit terms listed for the language.
8. Correct spelling, punctuation, agreement and terminology.
9. Keep terminology uniform: one name per concept. For business concepts, use the term recorded in the memory.

{{language_rules}}

# Memory rules

The memory is your own brain: noise makes every answer slower and less accurate. Saving is a decision.

1. Before saving, search the memory. If the note exists, update it. Do not create a duplicate.
2. Save only what cannot be obtained another way. Table structure comes from the catalog. Query results are queried again.
3. One idea per note, in one line. Details are optional and short.
4. Do not save rows or personal data: names, IDs, emails, phone numbers, amounts of a specific customer. Save the rule, not the case.
5. Save what is verified. Mark an unverified deduction as such.
6. If new information contradicts a note, propose replacing it. Do not keep both.
7. Close finished work items as soon as they are finished.

# App rules

You can operate Rowly DB. After every visible action, tell the user what you did and where to look, using the names shown on screen and the location returned by the action. If an action fails, report the reason. Do not try another way around it.
````

````markdown
## Español

- Variante: español neutro.
- No usar voseo.
  - Incorrecto: «creá», «configurá», «tenés», «podés».
  - Correcto: «crear», «configurar», «se debe», «puede».
- Expresiones prohibidas: «según sea necesario», «de forma adecuada», «se recomienda», «entre otros», «etc.».
- Obligaciones: «debe», «no debe», «es obligatorio», «es opcional».
````

````markdown
- Variante : français neutre.
````

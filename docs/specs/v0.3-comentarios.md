# Comentarios — diseño

## Estado

**En curso.** Este documento es la fuente de verdad: cada parte registra su
estado, lo decidido y lo que falta.

Última actualización: 2026-10-02.

## Objetivo

Los comentarios del editor SQL se comportan como en otros editores y se leen
bien, sin dejar de ser comentarios grises:

1. El editor entiende los comentarios **como el motor conectado**: dónde
   empieza y acaba cada uno, y qué parece un comentario pero es código.
2. `/*` se cierra solo, como en cualquier editor.
3. Dentro del comentario hay jerarquía tipográfica (negrita, cursiva,
   monoespaciada), siempre en gris.

**Fuera de alcance:** la vista legible de comentarios al estilo PhpStorm, y
cualquier cosa al estilo de Better Comments (colores por prefijo como `!`,
`?` o `TODO`). Eso irá en una extensión aparte. Lo nativo se queda en las tres
partes de arriba, para que la extensión tenga una base correcta sobre la que
construir.

## Cómo se comporta cada motor

Comprobado contra los servidores de `tools/test-dbs` el 2026-10-02.

| | MySQL | MariaDB | PostgreSQL | SQL estándar (sin conexión) |
|---|---|---|---|---|
| `-- ` | necesita un espacio o control detrás (`--x` es `-` `-x`) | igual | cualquier carácter | cualquier carácter |
| `#` | comentario de línea | comentario de línea | operador | no |
| `/* */` anidado | no: acaba en el primer `*/` | no | sí | no |
| `/*! … */`, `/*!50001 … */` | **código**, según la versión | **código** | comentario | comentario |
| `/*M! … */` | comentario | **código** | comentario | comentario |
| `/*+ … */` | pistas del optimizador | pistas desde 12.0; antes, comentario | comentario (solo `pg_hint_plan` las lee) | comentario |

Prueba en MySQL 8.4: `SELECT 1 /* a /* b */ ; SELECT 'x'; */` ejecuta las dos
sentencias. El comentario acaba en el primer `*/` y la segunda sentencia corre.

Pistas: una pista inválida da el aviso «Optimizer hint syntax error» en MySQL 8.4
y en MariaDB 12.0, 12.3 y 13.0; MariaDB 11.8 la ignora. El cliente `mariadb`
quita los comentarios antes de enviarlos si no se le pasa `--comments`.

## Parte 1 — Entender los comentarios como el motor

### Lo que falla hoy

- **El resaltado (`@codemirror/lang-sql` 6.10.0)** anida `/* */` en todos los
  dialectos y pinta `/*! … */` y `/*+ … */` como comentarios. En MySQL, el
  ejemplo de arriba se ve todo gris, como si el `SELECT 'x'` (o un `DROP`)
  estuviera comentado, y se ejecuta.
- **El divisor (`sqlStatements.ts`)** acierta, pero decide las reglas por señales
  indirectas: anida cuando el motor tiene `dollarQuotes`, trata `/*!` como código
  y exige el espacio tras `--` cuando tiene `hashComments`, y no conoce `/*M!`.
  El guard de Rust sí distingue `/*M!` (`execution_guard.rs`).

No hay hueco de seguridad: el divisor y el guard cortan bien y el guard rechaza
el texto con dos sentencias (SQL_ENGINE S1, S2). El problema es que el editor
muestra como comentado código que se ejecuta.

### Diseño

`SqlLexical` (`sqlStatements.ts`) declara las reglas, sin deducirlas de otras:

```ts
interface SqlLexical {
  // …lo que ya hay
  nestedComments: boolean;            // /* /* */ */ (Postgres)
  dashCommentNeedsSpace: boolean;     // "-- " y no "--x" (MySQL, MariaDB)
  executableComments: readonly ("/*!" | "/*M!")[];   // MySQL: ["/*!"]; MariaDB: ["/*!", "/*M!"]
  optimizerHints: boolean;            // /*+ … */ (MySQL; MariaDB desde 12.0)
}
```

- **Divisor:** usa estos campos en vez de `dollar`/`hash`. Sus pruebas de contrato
  (`engines/contract.test.ts`) suman los casos de la tabla de arriba.
- **Resaltado:** el dialecto de cada motor (`dialectFor`, `sqlSchema.ts`) envuelve
  el parser de lang-sql con `parseMixed` (`@lezer/common`), que vuelve a analizar
  como SQL lo que el motor ejecuta:
  - el interior de `/*! … */` y `/*M! … */`, tras el número de versión, según
    `executableComments`;
  - sin `nestedComments`, lo que sigue al primer `*/` de un comentario que
    lang-sql alargó por un `/*` interno.

  Los marcadores (`/*!50001`, `*/`) quedan como comentario; el interior, con los
  colores de SQL. Probado: `SQL_NO_CACHE` y `count` salen como palabras clave.
  Coste medido en un volcado de mysqldump de 20 000 líneas (1 MB) con un
  `/*!40101 … */` por sentencia: el análisis completo pasa de 133 a 236 ms.
  CodeMirror analiza por partes, empezando por lo visible, así que no bloquea.
- **Pistas `/*+ … */`:** siguen siendo comentario, con el nombre de cada pista
  en negrita (Parte 3). En MariaDB dependen de la versión (desde 12.0). Hasta que
  la línea viaje con la conexión (`v0.3-soporte-de-versiones.md`, fase 3), el
  perfil de MariaDB las activa siempre. Es solo visual: el texto sigue gris en
  las dos formas.
- **Upstream:** CodeMirror no acepta código escrito por IA (su CONTRIBUTING) y
  ya no recibe PR en GitHub (code.haverbeke.berlin). No se envía un PR. Se
  redacta un reporte de bug, que el usuario presenta si quiere. La envoltura
  local resuelve el problema; si algún día lang-sql trae la opción, la segunda
  parte de la envoltura se quita.

## Parte 2 — Cierre automático

| Se escribe | Resultado |
|---|---|
| `/*` | `/*│*/` (el cursor en `│`) |
| Enter entre `/*` y `*/` | `/*`, ` * │` y ` */` en tres líneas, con la sangría de la línea |
| Enter dentro de un bloque cuya línea empieza por ` * ` | la línea siguiente empieza por ` * ` |
| `*/` justo antes de un `*/` que puso el editor | se salta, no se duplica |
| Backspace justo después de `/*` en un `/*│*/` vacío | borra el par |

- No actúa dentro de un texto, un identificador entre comillas ni otro
  comentario: lo decide el árbol de sintaxis, que ya conoce las reglas del motor
  (Parte 1).
- En `/*!` y `/*M!` también cierra: siguen terminando en `*/`.
- `--` y `#` no necesitan cierre.
- Lo que ya existe sigue igual: `Ctrl+/` comenta la línea con `-- ` (válido en los
  tres motores) y `Shift+Alt+A` comenta un bloque.

## Parte 3 — Jerarquía tipográfica, en gris

Todo sigue en el gris de los comentarios del tema. Solo cambian el peso, el
estilo y la familia de la fuente:

| Elemento | Cómo se ve |
|---|---|
| Texto del comentario | gris, recto |
| Marcadores `--`, `#`, `/*`, `*/`, ` * ` de continuación | gris más tenue |
| `TODO`, `FIXME`, `NOTE`, `HACK`, `XXX` al principio de una frase | **negrita** |
| Etiquetas `@param`, `@return`, `@deprecated`… | **negrita** |
| `**texto**` | **negrita** (los asteriscos, tenues) |
| `*texto*` y `_texto_` | *cursiva* (los marcadores, tenues) |
| `` `texto` `` | monoespaciada, recta |
| Nombre de una pista en `/*+ NO_INDEX(t) */` | **negrita** |

- **Texto recto en vez de cursiva.** Hoy todo el comentario va en cursiva
  (`codemirrorTheme.ts`). Si la base es cursiva, `*texto*` no se distingue. Por
  eso la base pasa a recta y la cursiva queda para el énfasis.
- Lo pinta una decoración sobre los comentarios **visibles**, nunca sobre todo
  el documento (SQL_ENGINE, rendimiento con documentos grandes).
- No se aplica dentro de `/*!` ni `/*M!`: es código.
- El marcado no se toca: lo escrito queda tal cual en el archivo.

# Perfiles de motor — diseño (tarea 17)

Todo lo que hace el editor (autocompletado, alias, JOIN por FK, Error Lens,
análisis, rendimiento con documentos enormes) tiene que valer para **cada
motor que se agregue**, no solo para MySQL y PostgreSQL. Hoy lo que cambia
de un motor a otro está repartido en más de diez lugares, casi siempre como
`driver === "postgres" ? … : mysql`, y con **MySQL como caso por defecto**:
un motor nuevo heredaría en silencio el comportamiento de MySQL, sin que nada
falle al compilar ni en las pruebas.

La idea: **un perfil por motor** que reúna todo lo que es propio de él, y
que el resto del código solo le pregunte al perfil. Agregar un motor pasa a
ser escribir su driver en Rust y su perfil; lo demás llega solo.

---

## 1. Qué ya es de todos los motores

Sale del texto de la sentencia o del catálogo (que cada driver entrega con la
misma forma, `CatalogTable`), así que no hay nada que tocar:

- Índice de sentencias incremental, documentos de 1M líneas (tarea 15).
- Error Lens: `RangeSet`, pintar solo lo visible, análisis de fondo con
  caché, sentencia en escritura.
- Autocompletado: resaltado, alias automáticos, JOIN y ON por FK, columnas
  calificadas (tarea 16).
- Consolas grandes en disco, historial, resultados, exportar.

## 2. Inventario: lo que depende del motor

### Frontend

| Qué | Dónde | Hoy |
|---|---|---|
| Lista de motores, puerto, backend | `connections.ts` | `getDriver` cae a MySQL si no encuentra |
| Dialecto de CodeMirror (keywords, resaltado) | `sqlSchema.ts` `dialectFor` | ternario, cae a MySQL |
| Palabras que abren sentencia | `sqlCompletionPolicy.ts` | ternario, cae a MySQL |
| Comillas de identificadores | `filterBuilder.ts` `quoteSqlIdentifier`, `Workspace.svelte` | ternario, cae a MySQL |
| Formateador | `sqlFormatter.ts` | ternario, cae a MySQL |
| Ayuda por código de error | `sqlErrorHelp.ts` | tabla mezclada de SQLSTATE y códigos de MySQL |
| Ubicar un error de ejecución | `sqlDiagnostics.ts` `errorRange` | posición de Postgres y mensajes `near '…'` de MySQL mezclados |
| Palabras reservadas para alias | `sqlRelations.ts` | lista corta mezclada + keywords del dialecto |
| Cortar en sentencias | `sqlStatements.ts` | superconjunto fijo: `'` con `\`, `"`, `` ` ``, `--`, `/* */`, `$tag$` |
| Clasificar el contexto del cursor | `sqlContext.ts` (lexer) | superconjunto fijo, `#` como comentario siempre |
| URL de conexión, TLS | `ConnectionForm.svelte` | `backendKind === "mysql" ? … : postgresql` |

El superconjunto de los dos últimos se equivoca en casos reales: en
PostgreSQL `'C:\'` es un string completo (la `\` no escapa), en MySQL `#`
abre un comentario y en PostgreSQL no; y un motor nuevo trae lo suyo
(`[nombre]` y `GO` en SQL Server, bloques `BEGIN … END;` y `/` en Oracle).

### Backend (Rust)

| Qué | Dónde | Hoy |
|---|---|---|
| Motor ↔ dialecto | `drivers.rs` `DatabaseKind::dialect` | `match` exhaustivo (bien) |
| Parser del análisis | `engine/src/lib.rs` `as_sqlparser_dialect` | `match` exhaustivo (bien) |
| Comillas, literales, `INSERT` vacío, mayúsculas | `engine/src/editing.rs` | varios `dialect == Dialect::Postgres` (el resto cae a MySQL) |
| Paginar, ordenar, contar | `engine/src/pagination.rs` | por sqlparser, sin ramas propias |
| Guardia de destructivas | `engine/src/execution_guard.rs` | por sqlparser |

## 3. El perfil (frontend)

`lib/engines/`: un archivo por motor y un índice.

```ts
export interface EngineProfile {
  id: ConnectionDriver;          // "mysql" | "mariadb" | "postgres" | …
  backend: BackendKind;          // el driver de Rust que lo atiende
  // Como se escribe el SQL
  lexical: {
    identifierQuotes: readonly ('"' | "`" | "[")[];
    backslashEscapes: boolean;   // '\'' escapa (MySQL) o no (Postgres)
    hashComments: boolean;       // # abre comentario (MySQL)
    dollarQuotes: boolean;       // $tag$ … $tag$ (Postgres)
  };
  quoteIdentifier(name: string): string;
  // Editor
  editorDialect: SQLDialect;     // CodeMirror (lang-sql)
  formatterDialect: FormatterDialect;
  statementStarters: readonly string[];
  reservedWords: ReadonlySet<string>;   // un alias asi rompe la consulta
  // Errores de ejecucion
  errorHelp: Readonly<Record<string, ErrorHelp>>;  // por codigo del servidor
  locateError(statement: string, error: { message: string; position?: number }): Range | null;
}
```

- `ENGINES: Record<ConnectionDriver, EngineProfile>`: el tipo obliga a que
  cada motor tenga su perfil. Agregar `"sqlserver"` a `ConnectionDriver` sin
  su perfil **no compila**. `engineFor(driver)` nunca cae a otro motor.
- MariaDB parte del perfil de MySQL y cambia lo suyo (su dialecto de
  CodeMirror, `MariaSQL`).
- El índice de sentencias y el lexer del contexto reciben `lexical`: el
  índice va en un `Compartment` que se reconfigura al cambiar de conexión
  (vuelve a escanear, de fondo, como al abrir).

## 4. El perfil (Rust)

- `Dialect` gana métodos con `match` exhaustivo en vez de comparaciones
  (`quote_ident`, `string_literal`, `empty_insert`, `folds_unquoted_to_lower`,
  `sqlparser`). Un motor nuevo en el enum rompe la compilación en cada lugar
  que tiene que decidir algo, nunca cae a otro motor.
- `DatabaseKind` ↔ `Dialect` sigue siendo el único cruce entre el driver y el
  engine.

## 5. Contrato de pruebas

Una batería común que corre **sobre cada perfil**, del lado del frontend y
del backend. Cuando llegue un motor nuevo, se le suma y tiene que pasarla:

- Cortar sentencias con sus comillas, comentarios y bloques; un `;` dentro de
  cada forma de string o comentario del motor no corta.
- Comillas de identificadores: ida y vuelta con el carácter de comilla
  adentro.
- Alias automáticos que no sean palabras reservadas del motor.
- El autocompletado de punta a punta (FROM, JOIN con alias, ON) con el
  dialecto del motor.
- Ubicar un error: con los mensajes reales que da ese servidor.
- Rust: literales y comillas que el parser del propio motor vuelve a leer
  igual (`sqlparser`).

## 6. Agregar un motor (guía)

1. Driver en `crates/drivers/<motor>` (el trait `DbConnector`).
2. Variante en `DatabaseKind` y `Dialect`: el compilador marca cada lugar a
   completar.
3. Perfil en `app/src/lib/engines/<motor>.ts` y su entrada en `ENGINES`: el
   compilador marca que falta.
4. Sumar el perfil al contrato de pruebas y correrlo.
5. Logo, puerto por defecto y formulario de conexión (`connections.ts`).

## 8. Hecho (2026-09-27)

- **17a** — `app/src/lib/engines/`: `types.ts` (`SqlProfile` para el editor,
  `EngineProfile` = eso más la URL de conexión), `common.ts` (lo estándar),
  `mysql.ts`, `mariadb.ts` (hereda de MySQL con su dialecto y formateador),
  `postgres.ts` y `standard.ts` (SQL estándar, solo para el editor sin
  conexión: explícito, nunca otro motor). `ENGINES: Record<ConnectionDriver,
  EngineProfile>`. `getDriver` ya no cae al primero de la lista, y la
  validación de los perfiles guardados acepta los motores de `ENGINES`.
- **17b** — Consultan el perfil: `dialectFor`, la política del
  autocompletado (`statementStarters`), `aliasFor` (reservadas del perfil más
  las keywords del dialecto), comillas de los filtros, formateador, URL y TLS
  del formulario, ayuda por código (`SqlDiagnostic.help`, calculada al crear
  el diagnóstico) y dónde cae un error (`errorRange` se partió en
  estrategias: `byServerPosition`, `byAnalyzerLocation`, `byNearFragment`,
  `byQuotedName`, y cada motor compone las suyas). `activeEngine` (store): el
  perfil de la conexión activa.
- **17c** — `SqlLexical` vive en `sqlStatements.ts` (el módulo más bajo, sin
  ciclos). El escáner compila las reglas de cada motor (comillas, `#`, `\`,
  `$tag$`, `[…]`) y el índice las recibe por la Facet `sqlLexical`, en un
  `Compartment` que se reconfigura al cambiar de motor (el índice se vuelve a
  armar y el análisis revisa todo). El lexer del contexto
  (`classifyContext`, `sqlTokens`, `statementRelations`) también.
- **17d** — `Dialect` en Rust: `folds_unquoted_to_lowercase`,
  `backslash_escapes`, `quote_identifier`, `string_literal`,
  `insert_defaults`, todos con `match` exhaustivo. Sin comparaciones
  `dialect == …` en el código.
- **17e** — `engines/contract.test.ts` (cada perfil, más el estándar: cortar
  sentencias, `\`, literales e identificadores que se vuelven a leer igual,
  alias no reservados, autocompletado de punta a punta; y por motor, un error
  real del servidor con `FIXTURES`, que el tipo exige para cada motor). El
  contrato en Rust (`crates/engine/src/lib.rs`): literales e identificadores
  que el tokenizer del propio motor lee igual, y la fila por defecto válida;
  un `match` obliga a sumar un motor nuevo a la lista. Las pruebas del índice
  incremental corren sobre las reglas de cada motor. Guía en
  `CONTRIBUTING.md`.

### Errores reales que aparecieron

- **Filtros y «copiar como INSERT» en MySQL**: la barra invertida no se
  escapaba (`C:\` rompía el literal). Ahora `quoteString` del perfil.
- **Exportar a archivo en SQL** (Rust): lo mismo; ahora
  `Dialect::string_literal`, el mismo que usa la edición de resultados.
- **Cortar en sentencias en Postgres**: `'C:\'` es un texto completo en
  Postgres y el escáner lo leía como un escape de MySQL; `#` se tomaba como
  comentario (en Postgres es un operador).
- **Ubicar un error en Postgres sin posición**: el nombre va entre comillas
  dobles y solo se buscaban simples.
